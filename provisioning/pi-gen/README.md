# Building a flashable image

A pi-gen stage that produces an SD card image with LP Frame already on it:
Raspberry Pi OS Lite 64-bit, our package, an AirPlay 2 `shairport-sync`, the
boot configuration, and a third partition for `/var/lib/lpframe`.

Flash it, set a username in Raspberry Pi Imager, boot. No OS install, no
compiler, no installer run.

```bash
sudo ./provisioning/pi-gen/build-image.sh
# → dist/YYYY-MM-DD-lpframe-lpframe.img.xz
```

An hour and about 12GB of disk. Most of the hour is `shairport-sync`
compiling under emulation.

## What it produces

| Partition | | |
|---|---|---|
| 1 | FAT | `/boot/firmware` — plus `lpframe-README.txt` |
| 2 | ext4 | the system |
| 3 | ext4 | `/var/lib/lpframe`, 2GB, labelled `lpframe` |

The root partition does **not** expand on first boot: partition 3 sits
immediately after it. See [the resize note](#the-resize-token) below.

## No credentials, anywhere

The image has no user account, no password, no SSH host keys and no web
interface password. That is the whole point — an appliance image with a
default login is a device on somebody's network with a password everyone
knows, and one flashed a hundred times is a hundred of them.

* **User and SSH** come from Raspberry Pi Imager's customisation, or a
  `userconf.txt` on the boot partition. `build-image.sh` sets neither
  `FIRST_USER_PASS` nor `ENABLE_SSH`.
* **SSH host keys** are generated on the device at first boot, as they are in
  any Raspberry Pi OS image.
* **The web password** is generated by `artd` the first time it starts, on
  the device, and stored as an Argon2id hash. `01-run-chroot.sh` fails the
  build if any device state appears during it — nothing of ours should run
  while the image is being made, and a baked-in password is the failure that
  check exists to catch.

Because the text console is masked (the renderer needs uncontended DRM
master), **a card flashed without Imager customisation has no way in at
all**. `lpframe-README.txt` on the boot partition says so, and says how to
recover with a hand-written `userconf.txt`, because the boot partition is
FAT and readable from the machine that flashed the card.

## How it is put together

```
stage-lpframe/
  prerun.sh                     copy the previous stage's rootfs
  EXPORT_IMAGE                  makes this stage produce an .img
  00-lpframe/
    00-run.sh                   host side: stage the .deb and the installer
    01-run-chroot.sh            in the image: install, then run install.sh
    files/README-FIRST.txt      lands on the boot partition
```

Two things are worth knowing before changing any of it.

**The image is built by running the real installer.** `01-run-chroot.sh`
installs the cross-built `.deb` and then calls `provisioning/install.sh
--skip-lpframe --yes`. Everything else — `shairport-sync` from source, the
KMS overlay and CMA size, journald to RAM, masking `getty@tty1`, enabling the
units — is the same code path a hand-installed device gets. If `install.sh`
has a bug then so does the image, which is the correct coupling: the
alternative is a second, untested description of how to set up a device,
which drifts.

`systemctl enable` is a filesystem operation and systemd does it offline when
it detects a chroot, so that half works during a build. Starting anything
does not, and `install.sh` checks for `/run/systemd/system` before trying.

**`NN-run.sh` must be executable.** pi-gen logs `Skip … (not executable)`
among thousands of other lines and cheerfully produces an image with none of
your software in it. `build-image.sh` re-applies the mode, and
`crates/lpframe-config/tests/packaging.rs` fails if the repository loses it.

## The resize token

Raspberry Pi OS expands the root partition on first boot. With a data
partition immediately after root, that must not happen, so
`01-run-chroot.sh` removes one bare word from `cmdline.txt` and then asserts
it is gone.

The mechanism is `resize_early`, an initramfs `local-premount` script from
`raspberrypi-sys-mods`, and its first act is:

```sh
if ! grep -q ' resize' /proc/cmdline; then
  exit 0
fi
```

Not `init=/usr/lib/raspberrypi-sys-mods/firstboot`, and not
`init=/usr/lib/raspi-config/init_resize.sh` — those are earlier mechanisms
that most guides online still describe. On a current image the bare word is
the one that matters.

(`resize_early` would in fact refuse anyway: it only resizes when root is
partition 2 with nothing after it. Relying on someone else's safety check to
protect our data is not a plan.)

## The data partition

`add-data-partition.sh` appends partition 3 after pi-gen has finished.

It only ever operates on a file — never a block device, never a loop device,
never as root. `mke2fs -d` builds a populated filesystem image directly and
`sfdisk` edits a partition table in a regular file, which means the thing
that writes a partition table is testable rather than merely reasoned about.
The tests assert that the root partition comes out byte-identical.

The filesystem ships empty apart from its label. `StateDirectory=lpframe` in
`lpframe-artd.service` sets the ownership when the daemon first starts, so
nothing here has to know what uid the image gave `lpframe`.

Space on the card beyond partition 3 is unused. That is the cost of a
writable partition that survives a read-only root; growing root afterwards is
possible but is not something an image should do to a card unasked.

## Building it yourself

Needs root — pi-gen wants loop devices, `chroot` and binfmt.

```bash
sudo apt-get install -y quilt parted qemu-user-static debootstrap zerofree \
    zip dosfstools libarchive-tools libcap2-bin grep rsync xz-utils curl \
    xxd file git kmod bc gpg pigz arch-test kpartx

sudo ./provisioning/pi-gen/build-image.sh
```

| | |
|---|---|
| `--deb PATH` | use a package you already built |
| `--data-size MiB` | partition 3's size (default 2048) |
| `--hostname NAME` | default `lpframe` |
| `--no-compress` | leave a raw `.img` |
| `PI_GEN_REF=…` | a different pi-gen commit |

pi-gen is pinned to a **commit**, not a branch: an image build that silently
follows someone else's default branch is not reproducible and is not
something to hand anyone. 64-bit images come from pi-gen's `arm64` branch —
`master` hard-codes `ARCH=armhf`.

## Why shairport-sync is compiled

Debian trixie ships `shairport-sync` 4.3.7-1 built **without** AirPlay 2: no
`libplist`, `libsodium`, `libgcrypt` or ffmpeg among its dependencies, and no
relationship to `nqptp`. The version number is identical to the one we build
from source, so `shairport-sync -V` reporting 4.3.7 says nothing about
whether AirPlay 2 is in it — which is why `install.sh` tests for the
`AirPlay2` marker rather than the version, and does the right thing on a
device where the distro package is already installed.

When Debian catches up, that check will find a working packaged build and the
compile step disappears on its own.

## Verified, and not

`add-data-partition.sh` is tested for real: against a pi-gen-shaped image
with a populated ext4 root, asserting the new filesystem mounts with the
right label and that the root partition is byte-identical afterwards.

The pi-gen build itself has only ever run in CI, and **no image produced by
it has been booted on hardware.** Until one has, treat a green build as
evidence that the pieces assemble, not that the result works.
